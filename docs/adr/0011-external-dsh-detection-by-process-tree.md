# 0011. 外部 dsh 探测按进程树排除 Hub 托管实例

- 状态：已采纳
- 日期：2026-10-20

## 背景

「创建实例时接管当前本地运行的 dsh」这条链路一直存在：`scanExternal`（只读探测）→ 向导复选框 / 详情页接管卡片 → `adoptExternal`（主进程重扫按 pid 认定）→ `runtime.adopt` → token 入库。

但探测阶段长期失配：判定函数 `isDshWebCommand()` 只认旧命令行形态 `dsh web …`，而当前 dsh CLI 已把 profile 改为 `--profile` 形态（`dsh <name>` 是 `dsh --profile <name>` 的缩写）。用户按当前文档敲的 `dsh --profile web …` 一条都认不出来，扫描返回空数组，向导与详情页的接管入口整块不渲染 —— 表现为「接管功能没了」，实际是探测失配。

失配之所以长期无人发现：单测与 E2E 夹具都只用旧形态。E2E 的假 dsh 是 `node -e … /tmp/fake-dsh/dsh web --patch …`，命令行里含 `dsh web`；单测也只断言旧形态。夹具形态与真实形态脱节，回归无人可见。

修复时有个硬约束：Hub 自己拉起的实例与用户手敲的 dsh **命令行完全同形**（同为 `dsh --profile web …`）。原先「Hub spawn 的进程没有 `web` 子命令，天然被排除」这条排除依据，在 Hub 自己改用 `--profile` 启动（2026-09-18，`94c0b57`）之后已经失效。只放宽正则会让 Hub 把自己的实例报成「外部未纳管进程」，并允许用户接管自己 —— 那会导致接管语义混乱（Hub 托管的实例被标成 `runtimeSource=external`，停止时不再终止进程）。

## 决策

1. **命令行判定与「是不是 Hub 拉起的」拆成两件事**：命令行判定只回答「这个进程是不是一次 dsh web profile 启动」：
   - 入口 token：`…/dsh`、`…/dsh.js`、`…/@deepseek-ai/dsh/lib/bin.js`（以 token 结尾判定，目录名带 dsh 的其它程序不算）；
   - profile 形态：`dsh web …`（旧）与 `dsh --profile web …` / `--profile=web`（当前）；
   - `dsh plugin --profile web …` 是插件管理命令，不提供工作区，必须排除。
2. **是否由 Hub 拉起，按进程树判定**：探测时带出每个进程的父 pid（POSIX `ps -axo pid=,ppid=,command=`；Windows `Get-CimInstance Win32_Process` 带出 `ParentProcessId`），以 Hub 主进程 pid 为根收集整棵子树，落在子树里的 dsh 一律不作为外部实例上报。dush / duush 是包装器、再 spawn dsh，dsh 是孙进程，按祖先链判定两层都能覆盖。
3. **dsh / dush / duush 一视同仁，但探测对象是 dsh 进程**：包装器（dush/duush）自己 spawn 一个 dsh 子进程去提供工作区，**监听端口由那个 dsh 持有**（实机验证：duush 起 `127.0.0.1:32456`，持有者是它 spawn 的 dsh 子进程，包装器自身不监听工作区端口）。因此探测只认 dsh 入口，包装器本身不作为可接管对象上报 —— 把它当可接管对象会把用户引到错误的端口（包装器自己可能另开登录、采集等本地服务端口）。用 dush/duush 起的工作区照样能认出来，认的是它们拉起的那个 dsh。
4. **E2E 夹具与真实形态对齐**：夹具改成当前 CLI 形态 `--profile web`，并额外起一个旧形态 `web` 的进程，两者并存，验证探测不挑形态。
5. **向导里的接管对象必须让用户选**：探测可能同时返回多个 dsh（用户自己起了几个、开发实例、别的工具拉起的），而向导一次只能接管一个。默认取「注册表里已有本机实例、地址与它一致」的那个，其次端口最小的一个（顺序固定，不随扫描返回顺序漂移）；多个候选时用下拉让用户挑 —— 端口各不相同，接管错一个就白填一次 token。
6. **进程树之外再按端口兜一层**：进程树覆盖不到一种情形 —— 包装器进程先于它的 dsh 子进程退出时，POSIX 把 dsh 改挂到 pid 1，它就脱离了 Hub 主进程的子树，于是 Hub 托管的实例会被当成外部实例上报，用户接管它之后停止时不再终止它，进程泄漏。因此端口确定之后再排一次：**Hub 自己 spawn 的实例**所占的端口不是可接管对象。同一时刻一个端口只能被一个进程绑定，所以按端口排除不会误伤用户自己起的 dsh；端口也不受进程重启与 pid 复用影响。
   - 只排除 Hub **spawn** 的实例，不排除**接管**进来的：接管进来的外部实例本来就该继续作为「外部 dsh」被识别（详情页的接管卡片靠它出现），排除掉就再也接管不了第二次。
7. **`hubPid` 必填**：排除 Hub 托管实例全靠进程树规则，取值错了（例如 0）就会把 Hub 自己的实例报成外部实例。留成可选等于把这条防线交给每个调用方的自觉，因此改成必填，让编译器强制表态。
8. **扫描结果里的命令行脱敏后才出主进程**：探测命中面比修复前宽（`--profile web` 出现在参数表任意位置即命中），而 dsh 的 token / cookie 形态就写在命令行上。命令行走 `redactSecret` / `redactLine`（`@shared/redact`）脱敏后再交给界面，脱敏发生在构造处而不是 IPC 出口，让「已脱敏」成为类型契约而不是每个调用点的自觉。

## 被否决的备选

- **只放宽正则，加上 `--profile web`**：会把 Hub 自己托管的实例报成外部实例，用户可以「接管」自己的实例，实例状态从 `hub`/`path` 变成 `external`，停止时不再终止进程 —— 进程泄漏，且 Hub 失去对自己实例的生命周期管理。
- **按 Hub 记录的 spawn pid 集合过滤（方案 B）**：Hub 只直接 spawn 启动器包装器，dsh 是孙进程，pid 集合覆盖不全；且包装器把子进程 pid 透传给 Hub 需要改 dush/duush 的协议，跨仓库改动成本高于收益。
- **按命令行里的可执行路径区分（hub 的隔离目录 vs 用户 PATH）**：Hub 的 `path` 来源实例用的就是用户 PATH 上的 dsh，与用户手敲的完全同形，区分不了。
- **按监听端口区分归属**：端口可被任意占用，不能单独作为归属依据。但**排除**方向可以：Hub 托管实例占着的端口上不可能同时坐着另一个 dsh，因此端口适合用来「排除已知属于 Hub 的端口」，不适合用来「认定归属」。
- **按 `DSH_HOME` 环境变量区分**：环境变量不在进程命令行里，取不到。
- **Windows 侧按命令行含 dsh 预过滤**：看起来能省输出量，但会把祖先链切断 —— dush / duush 包装器的路径不含 "dsh"，包装器这一层缺失后，它的 dsh 子进程接不回 Hub 主进程，Hub 托管的实例反而会被报成外部实例。Get-CimInstance 本来就要取全表，过滤只发生在 PowerShell 侧，省不下查询成本却会丢掉进程树，因此不做过滤，改为把输出缓冲上限放宽（1MB → 16MB）。

## 后果

- 探测不再依赖命令行里某个子命令的位置，`dsh` 与新旧两种 profile 形态都能识别；用 dush/duush 起的工作区经由它们 spawn 的 dsh 进程被识别。
- 排除 Hub 托管实例的依据从「命令行形状」变成「进程树 ∪ 托管端口」，不再随 Hub 自身启动参数变化而失效。
- 进程表探测多取一个字段：POSIX 的 `ps` 与 Windows 的 CIM 都要带出父 pid；Windows 的 CIM 脚本同步调整为输出 `pid<TAB>ppid<TAB>command`。
- 向导在多个候选时多一个下拉框；单候选时界面与此前一致。
- 代价：进程表查询的输出量变大（Windows 侧从「只回传含 dsh 的进程」变成「回传整机进程表」，典型桌面约 70KB），需要放宽 execFile 的 maxBuffer，否则超限时子进程被杀、扫描静默返回空 —— 那正是本次要修的症状在 Windows 上回归。
- 残留缺口：进程表取不到 Hub 主进程自身（极少见）时，进程树规则整体失效，只剩端口兜底。
- 新增验收脚本 `scripts/acceptance/verify-external-dsh.cjs`：用**真实** dsh 打 live `ps`，断言「用户自己起的 dsh 被认出来且端口正确」与「Hub 托管的实例不被上报」。合成夹具与真实 CLI 形态脱节时门禁会全绿而功能已坏（本次缺陷正是如此），这份脚本是唯一能防住这一类漂移的东西。
