# 0012. 停止语义按「整棵进程树排空」判定

- 状态：已采纳
- 日期：2026-10-21

## 背景

用户在实例详情页点「重启实例」后，详情页弹出「本机已在运行的 dsh web」卡片，
列出 `127.0.0.1:3080 · pid 40967`，命令行显示 `dsh --patch /Users/ankh/.dsh/cordis.duush.patch.yml --profile web --port 3080 --no-open` —— 那个进程**正是 hub 刚刚重启掉的旧实例**。

复现链路（用真实 hub 代码复现，见 `src/main/local-runtime/local-runtime-drain.test.ts`）：

1. Hub spawn 出去的不是 dsh，而是**启动器包装器**（dush/duush）。包装器自己再 spawn 一个 dsh 子进程去提供工作区 —— 监听端口由那个 dsh 持有。
2. 停止时 hub 走 `killProcessGroup` → `process.kill(-pgid, 'SIGTERM')`，**整组同时收到 SIGTERM**。
3. 包装器**没有 SIGTERM 处理器**，收到信号立刻死。dsh 子进程被 reparent 到 init（脱离 hub 主进程的进程树），并继续走一段**异步优雅退出**：`process.on('SIGTERM')` → `shutdown.interrupt(0)` → `dispose()`（Cordis 根 fiber 拆卸，含关端口），最长 5 秒（dsh 的 `PROCESS_SHUTDOWN_TIMEOUT_MS`）。
4. 旧实现只等**直接子进程（包装器）**退出。它 2ms 就死了 → `stop()` 立刻返回「已停止」。
   但此刻 dsh 还在跑、还占着 3080。

于是 hub 认为实例已停，实际没停。后果有两条：

- **重启撞端口**：紧随其后的 `start()` 分配端口时 3080 仍被旧 dsh 占着，只能漂到别的端口。
- **旧 dsh 被当成「用户自己的 dsh」**：包装器一死，dsh 就不再是 hub 主进程的子孙（进程树规则失效），也还没进 hub 的托管端口集合（`managedPorts` 在条目删除后就没了）。此时 `scanExternal` 按 ADR 0011 的规则把它判定为**外部实例**上报 —— 详情页于是弹出「本机已在运行的 dsh web」。

## 决策

1. **停止完成的判据从「直接子进程退出」改为「整棵进程树排空」**：POSIX 下 `detached` spawn 的子进程自成进程组（组号 = 子进程 pid），用 `kill(-pgid, 0)` 探测组内是否还有存活成员，等到组排空才算停干净（`src/main/transport/process-tree.ts`）。
2. **排空等待有上限，超时升级强杀整组**：等待上限 6 秒（dsh 优雅退出上限 5 秒 + 1 秒余量）。超时则对整组发 SIGKILL，再短等一次确认。强杀后进程组必然排空（内核回收），确认不了也不阻塞停止流程。
3. **Windows 不走排空等待**：`taskkill /T /F` 同步杀整棵树，子进程退出即排空，没有「包装器先死、dsh 后死」的窗口。
4. **外部接管实例的停止语义不变**：仍然只断开接管、绝不终止用户自己的进程 —— 那条路径 hub 从没 spawn 过，没有进程组可排空。

## 后果

- 重启不再撞端口，旧 dsh 不会被误报成外部实例。
- 停止耗时变长：dsh 走完优雅退出才返回（实测 1.5–5 秒，取决于 dsh 的 disposer 快慢）。这是**正确的代价** —— 之前那 2ms 的「停止完成」是假的。
- 应用退出路径（`stopAll`）同样变长：各实例的排空等待并行进行，最多再等 6 秒。
- 排空探测只在 POSIX 生效；`process.kill(-pgid, 0)` 的 EPERM（成员还在、只是无权发信号）判为存活。

## 被否决的备选

- **给包装器加 SIGTERM 转发**（让它把信号转给 dsh 并等它退出）：能治 dsh/duush，但 hub 侧仍无法确认「整棵树已停」—— 包装器转发后自己先退出，hub 等到的还是包装器。治标不治本，且要改另一个仓库。
- **停止时按端口检查是否释放**：端口释放是 dsh 排空的结果，但端口可能被别的进程占用，且同端口不同实例的场景下判据不唯一。用进程组判定更直接。
- **只把旧 dsh 加进 `managedPorts` 黑名单**（让外部探测忽略它）：治的是「误报」这一半，但旧 dsh 仍占着端口，重启照样撞端口；而且黑名单里留一个不归 hub 管的进程，与「接管进来的外部实例不算托管」那条规则直接冲突。
- **把停止语义放宽成「不等待」**：等于承认端口可能被占，靠端口漂移兜底 —— 每次重启都换一个端口，用户拿到的地址不稳定。
